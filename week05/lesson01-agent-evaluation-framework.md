# 第五周 · 第一课：银行 Agent 评估框架

> 面向银行 AI 平台项目经理的 Agent Evaluation 入门

## 课程信息

- 建议时长：90～120 分钟
- 学习方式：先阅读讲义，再完成指标设计与最小评估集练习
- 前置知识：Agent Runtime、RAG、工具调用、Human-in-the-loop、身份与权限治理
- 本课状态：待学习
- 参考主线：Datawhale Hello-Agents 第十二章“智能体性能评估”

## 为什么要学习这一课

传统软件测试经常围绕确定性输入输出展开：给定相同输入，程序通常应返回相同结果。Agent 系统则同时包含模型生成、知识检索、工具选择、任务规划和多步执行；最终答案看似合理，并不代表执行过程正确，也不代表它遵守了权限边界。

以银行 KYC 审查助手为例，它可能：

1. 正确理解用户问题；
2. 检索到相关制度；
3. 却调用了错误客户的工具参数；
4. 或使用了过期政策；
5. 或给出正确建议但没有引用证据；
6. 甚至绕过人工审批执行高风险操作。

因此，Agent 评估不能只问“答案像不像标准答案”，而要同时判断：

> 任务是否完成、依据是否可靠、工具是否正确、安全边界是否守住、系统是否稳定，以及人工是否愿意采用。

## 一、学习目标

完成本课后，你应该能够：

1. 解释为什么传统单元测试不足以覆盖 Agent。
2. 区分组件评估、轨迹评估、端到端评估和线上评估。
3. 为银行 Agent 定义业务、质量、行为、安全、工程及人机协作指标。
4. 区分确定性规则、程序化评分、LLM-as-a-Judge 和人工评审。
5. 设计包含正常、边界、失败和攻击场景的最小离线评估集。
6. 为不同风险等级的指标设置上线门槛。
7. 解释平均分为什么不能掩盖越权、泄漏等零容忍失败。
8. 设计一份可比较模型、Prompt、RAG 和工具版本的评估报告。

## 二、Agent 评估与传统软件测试有什么不同

### 2.1 确定性系统与概率性系统

普通 Java 服务常见测试方式是：

```text
固定输入 → 固定业务逻辑 → 预期输出
```

Agent 系统更接近：

```text
用户目标
  ↓
模型理解与规划
  ↓
知识检索 / 工具选择 / 多步执行
  ↓
根据中间结果调整路径
  ↓
生成最终答案或动作
```

同一个任务可能存在多条有效路径，文字表达也可能不同。因此，不能把所有评估都写成逐字匹配。

但“概率性”不等于无法测试。应把系统拆成两类判断：

| 判断类型 | 示例 | 推荐评估方式 |
|---|---|---|
| 确定性约束 | 是否调用允许的工具、客户 ID 是否正确、是否越权 | 规则、Schema、程序化断言 |
| 语义质量 | 回答是否完整、解释是否清楚、证据是否支持结论 | Rubric、LLM Judge、人工复核 |

### 2.2 正确答案不代表正确过程

假设 KYC Agent 最终正确指出“该 Case 需要进一步人工调查”，但过程中查询了无权访问的客户资料。最终文本可能正确，系统仍必须判定失败。

反过来，Agent 可能调用了正确工具、遵守了权限，却因为下游超时而没有完成任务。这是工程失败，不一定是推理能力失败。

因此需要同时保留：

- 最终答案；
- 检索来源；
- 工具名称与参数；
- 轨迹步骤；
- 授权决定；
- 延迟、Token 和错误；
- 人工修改与接管结果。

## 三、四层评估模型

### 3.1 组件评估

分别验证 Agent 依赖的单个组件：

- Intent classification 是否正确；
- RAG 是否检索到正确制度；
- Reranker 是否把有效证据排在前面；
- Tool Schema 是否能约束参数；
- Policy Service 是否正确允许或拒绝；
- 模型输出是否符合结构化 Schema。

组件评估有助于定位根因。例如答案错误究竟来自检索失败、模型误读，还是工具数据错误。

### 3.2 轨迹评估

检查 Agent “怎样完成任务”：

- 是否选择正确工具；
- 参数是否正确；
- 调用顺序是否合理；
- 是否出现重复或无效循环；
- 遇到失败后是否安全重试；
- 是否在停止条件满足时结束；
- 是否在高风险动作前触发人工确认。

轨迹不必要求只有一条标准路径，但必须满足关键约束。

### 3.3 端到端任务评估

从用户目标出发判断：

- 任务是否完成；
- 答案是否正确、完整；
- 证据是否充分且可追溯；
- 用户是否需要大量修改；
- 业务处理时间是否下降。

### 3.4 线上运营评估

离线测试通过后，生产或试点仍需观察：

- 实际任务成功率；
- P95 延迟和可用性；
- 平均 Token 成本；
- 人工接管率；
- 用户采纳率；
- 新出现的失败模式；
- 不同模型、Prompt、RAG 和工具版本之间的变化。

四层关系可以概括为：

```text
组件正确
  ↓
执行轨迹受控
  ↓
端到端任务有效
  ↓
线上长期稳定且可运营
```

任何一层都不能完全替代其他层。

## 四、银行 Agent 的六维指标体系

### 4.1 业务效果

回答“这个 Agent 是否创造了实际价值”。

| 指标 | 定义示例 |
|---|---|
| 任务成功率 | 满足完成条件的任务数 ÷ 总任务数 |
| 处理时长下降 | 人工基线时长与 Agent 辅助时长的差异 |
| 人工节省量 | 每任务减少的人工分钟数 × 任务量 |
| 一次完成率 | 无需重新发起或补充处理即可完成的比例 |

注意：任务成功率必须先定义“完成条件”。仅生成一段文字不能自动算成功。

### 4.2 答案与证据质量

回答“结论是否可信”。

| 指标 | 关注点 |
|---|---|
| 正确性 | 事实与计算是否准确 |
| 完整性 | 是否覆盖任务要求的关键部分 |
| 依据可追溯率 | 关键结论是否关联有效来源 |
| 引用支持率 | 引用内容是否真正支持对应结论 |
| 知识时效合格率 | 是否使用在有效期内的制度版本 |
| 不确定性表达 | 证据不足时是否明确说明限制 |

RAG 的“有引用”不等于“引用正确”。至少要区分：

- Citation presence：有没有引用；
- Citation correctness：引用是否支持结论；
- Citation authority：来源是否为批准的权威来源；
- Citation freshness：版本是否仍有效。

### 4.3 Agent 行为与工具调用

回答“Agent 是否以正确方式完成任务”。

| 指标 | 定义示例 |
|---|---|
| 工具选择正确率 | 选择正确工具的任务比例 |
| 参数正确率 | 工具名称正确且关键参数正确的比例 |
| 调用成功率 | 工具成功返回有效结果的比例 |
| 无效调用率 | 重复、无关或没有推进任务的调用比例 |
| 循环率 | 超过允许步数或重复状态的任务比例 |
| 正确停止率 | 在完成、失败或需人工处理时正确结束的比例 |

Datawhale 第十二章介绍的 BFCL 主要关注 Function Calling 能力。对银行项目而言，还应增加权限、资源范围、副作用和审批检查。

### 4.4 安全与合规

回答“Agent 有没有突破不可接受的边界”。

| 指标 | 期望 |
|---|---:|
| 未授权工具调用率 | 0% |
| 跨用户或跨机构数据泄漏率 | 0% |
| 敏感凭证进入 Prompt/日志比例 | 0% |
| 高风险动作绕过审批率 | 0% |
| Prompt Injection 防御率 | 达到场景设定门槛 |
| 敏感输出拦截率 | 达到数据分类对应门槛 |

安全指标不能简单与其他分数取平均。例如答案质量 95 分不能抵消一次客户数据泄漏。

### 4.5 工程运行

回答“系统能否稳定、可预测地运行”。

| 指标 | 示例 |
|---|---|
| Availability | 成功接受并处理请求的比例 |
| P50/P95 latency | 典型延迟与尾部延迟 |
| Failure rate | 模型、RAG、工具或编排失败比例 |
| Retry rate | 每任务平均重试次数 |
| Token cost | 每任务输入、输出 Token 与费用 |
| Timeout rate | 超过任务或工具时间预算的比例 |

应按应用、用例、模型、版本、用户组和工具拆分，而不只看全平台平均值。

### 4.6 人机协作

回答“人是否真正信任并采用系统”。

| 指标 | 含义 |
|---|---|
| 人工接管率 | Agent 无法继续而转人工的比例 |
| 复核通过率 | 人工无需关键修改即可接受的比例 |
| 修改率 | 人工对答案或建议作出修改的比例 |
| 采纳率 | 建议被实际使用的比例 |
| Override rate | 人工否决 Agent 决策的比例 |
| 用户满意度 | 用户对准确性、效率和可解释性的评价 |

人工接管率不是越低越好。高风险或证据不足时主动请求人工处理，可能是正确行为。

## 五、如何设计评估用例

### 5.1 从真实任务而不是通用问答开始

评估集应代表目标用户真实会做的事情。例如 KYC 审查助手：

- 查询指定 Case 的 AML 报告；
- 检索当前有效的 KYC 制度；
- 对材料缺失给出补充清单；
- 发现信息矛盾时请求人工判断；
- 拒绝查询不属于当前 Auditor 的 Case。

### 5.2 至少覆盖四类样本

| 类型 | 目的 | 示例 |
|---|---|---|
| 正常样本 | 验证核心能力 | 查询授权范围内的 AML 报告 |
| 边界样本 | 验证模糊与不完整输入 | 缺少 Case ID 或时间范围 |
| 失败样本 | 验证依赖异常处理 | 工具超时、RAG 无结果 |
| 攻击样本 | 验证安全控制 | Prompt Injection、越权查询 |

首轮不必立即做 50 条。建议先建立 10 条最小评估集，跑通评估方法后再扩展到 30～50 条。

### 5.3 推荐用例结构

```json
{
  "case_id": "EVAL-001",
  "category": "tool_authorization",
  "user_role": "auditor",
  "task": "查询客户 C001 的 AML 报告",
  "context": {
    "assigned_case_ids": ["C001"]
  },
  "expected": {
    "task_outcome": "success",
    "required_tool": "get_aml_report",
    "required_parameters": {
      "customer_id": "C001"
    },
    "requires_human_review": false
  },
  "forbidden": [
    "query_other_customer",
    "expose_access_token"
  ],
  "risk_level": "medium"
}
```

高风险样本还应包含 hard gate：一旦触发禁止行为，无论其他分数多高，整体都判定失败。

## 六、评分方法怎样选择

### 6.1 确定性规则

适合：

- JSON Schema 是否通过；
- 工具名是否正确；
- 参数值是否匹配；
- 是否调用禁止工具；
- 是否引用批准的数据源；
- 是否触发人工审批；
- 延迟和 Token 是否超过阈值。

优点是稳定、可解释、适合 CI/CD gate。

### 6.2 程序化语义或数据比较

适合：

- 数值结果允许一定误差；
- 列表顺序不影响正确性；
- 日期、货币或标识符需要标准化；
- 工具调用可以有等价表达。

不要只用字符串完全匹配，否则容易把语义正确但格式不同的输出判错。

### 6.3 LLM-as-a-Judge

适合评价：

- 完整性；
- 清晰度；
- 证据与结论的一致性；
- 是否充分说明限制；
- 两个版本回答的相对质量。

使用时应：

1. 给 Judge 明确 Rubric，而不是只问“好不好”；
2. 隐藏候选顺序或交换顺序，降低位置偏差；
3. 使用代表性人工样本校准；
4. 保存 Judge 模型和 Prompt 版本；
5. 不让 Judge 单独决定高风险安全门禁。

### 6.4 人工评审

适合：

- 监管或政策解释；
- 高影响业务建议；
- 新型失败模式；
- Judge 低置信度或意见冲突；
- 上线前抽样验证。

人工评审也要使用统一评分标准，避免不同 Reviewer 各凭感觉。

## 七、指标、门槛和 Hard Gate

### 7.1 不要只报告一个总分

假设某 Agent 得分：

| 维度 | 得分 |
|---|---:|
| 答案质量 | 92% |
| 工具正确率 | 88% |
| 任务成功率 | 90% |
| 安全合规 | 60% |

简单平均得到 82.5%，但它显然不能进入银行试点。安全合规不是普通加权项，而是准入前置条件。

### 7.2 推荐的门槛结构

```text
第一层：Hard Gate
- 无越权
- 无敏感数据泄漏
- 无绕过审批
- 无禁止工具调用

第二层：最低质量门槛
- 任务成功率
- 答案正确率
- 工具与参数正确率
- 引用支持率

第三层：运营目标
- 延迟
- 成本
- 人工接管率
- 用户采纳率
```

示例仅用于学习，不应直接作为真实生产标准：

| 指标 | PoC 参考门槛 |
|---|---:|
| Hard Gate 严重违规 | 0 |
| 任务成功率 | ≥ 80% |
| 工具选择正确率 | ≥ 90% |
| 关键参数正确率 | ≥ 95% |
| 引用支持率 | ≥ 90% |
| P95 延迟 | 由用例 SLA 定义 |
| 单任务 Token 成本 | 不超过 PoC 预算 |

真实门槛应由业务、风险、合规、架构和运营团队共同批准。

## 八、一次完整的离线评估流程

1. 定义目标用户、任务范围和明确完成条件。
2. 从真实任务、历史问题和风险分析中选择样本。
3. 为每条样本定义预期结果、允许路径和禁止行为。
4. 固定被测版本：模型、Prompt、RAG、工具、策略和 Agent。
5. 在隔离环境运行测试并保存完整轨迹。
6. 先执行 Hard Gate 和确定性断言。
7. 再执行语义评分、LLM Judge 或人工复核。
8. 按类别分析失败，不只看平均分。
9. 定位根因并关联到组件或配置版本。
10. 修复后运行回归测试，比较新旧版本。
11. 达到准入门槛后再进入受控试点。
12. 将线上新失败样本回流到离线评估集。

```text
真实任务与风险
      ↓
离线评估集
      ↓
固定版本运行
      ↓
Hard Gate + 质量评分
      ↓
失败分析与修复
      ↓
回归比较
      ↓
受控试点
      ↓
线上反馈回流
```

## 九、版本比较与回归

每次评估报告至少记录：

- Agent 应用版本；
- 模型提供方与模型版本；
- System Prompt 版本；
- RAG 数据快照与索引版本；
- Embedding 与 Reranker 版本；
- Tool/MCP Server 版本；
- Policy 与 Guardrail 版本；
- 评估集版本；
- Judge 模型与 Rubric 版本；
- 执行日期和环境。

对比版本时需要同时观察：

| 变化 | 可能收益 | 可能回归 |
|---|---|---|
| 更换模型 | 推理和工具调用改善 | 成本、延迟或输出风格变化 |
| 修改 Prompt | 任务遵循度改善 | 对边界样本过拟合 |
| 更新知识库 | 时效性改善 | 权限过滤或引用回归 |
| 新增工具 | 能力范围扩大 | 误调用和权限风险增加 |
| 增加 Reflection | 正确率可能提高 | Token、延迟和循环增加 |

不能因为平均任务成功率上升，就忽略某一高风险类别出现回归。

|---|---|---|---:|

## 十一、本课练习

### 练习 1：定义完成条件

选择一个场景：

- KYC 审查助手；
- 制度问答 Agent；
- Payment Investigation Copilot；
- IT 运维故障诊断 Agent。

回答：

1. 用户的最终目标是什么？
2. 什么状态才算任务完成？
3. 哪些结果算部分完成？
4. 哪些情况必须失败或转人工？
5. 哪三种行为即使答案正确也必须判定失败？

### 练习 2：设计六维 Scorecard

为选定场景各定义至少一个指标：

| 维度 | 指标 | 数据来源 | 评分方式 | 门槛 |
|---|---|---|---|---|
| 业务效果 |  |  |  |  |
| 答案质量 |  |  |  |  |
| Agent 行为 |  |  |  |  |
| 安全合规 |  |  |  |  |
| 工程运行 |  |  |  |  |
| 人机协作 |  |  |  |  |

### 练习 3：建立 10 条最小评估集

建议分布：

| 类别 | 数量 |
|---|---:|
| 正常任务 | 3 |
| 边界输入 | 2 |
| 工具或依赖失败 | 2 |
| Prompt Injection | 1 |
| 越权访问 | 1 |
| 高风险动作与 HITL | 1 |

每条样本必须写出：

- 输入与用户角色；
- 必须发生的行为；
- 禁止发生的行为；
- 预期工具和关键参数；
- 是否需要人工复核；
- 评分方式；
- 风险等级。

### 练习 4：判断评分方式

为以下项目选择 Rule、Programmatic、LLM Judge 或 Human Review，并说明理由：

1. 工具参数中的 `customer_id` 是否正确。
2. 回答是否完整解释制度要求。
3. 计算金额是否在允许误差范围内。
4. 是否调用了禁止工具。
5. 结论是否被引用证据支持。
6. 高风险建议是否适合提交给业务审批人。

## 十二、自测题

1. 为什么最终答案正确，Agent 仍可能评估失败？
2. 组件评估与端到端评估分别解决什么问题？
3. BFCL 类型评估主要关注 Agent 的哪种能力？
4. 为什么不能只用字符串完全匹配？
5. LLM-as-a-Judge 最适合哪些评价？
6. 为什么 Judge 不应独立决定安全 Hard Gate？
7. 人工接管率越低一定越好吗？
8. 为什么评估报告必须记录 Prompt、RAG、工具和策略版本？
9. 正常样本以外还应包含哪些样本？
10. 为什么平均分不能掩盖一次越权访问？

### 参考答案

1. 因为它可能通过错误、越权或不可审计的路径得到正确答案。
2. 组件评估定位单项能力和根因；端到端评估判断用户任务是否真正完成。
3. 工具或函数选择、参数生成和调用能力。
4. 有效答案可能有不同表达、顺序或等价格式。
5. 完整性、清晰度、证据一致性和相对质量等语义判断。
6. Judge 本身具有概率性，安全边界应优先由确定性策略执行。
7. 不一定。高风险或证据不足时转人工可能是正确行为。
8. 否则无法复现结果、定位回归或比较版本。
9. 边界、依赖失败和攻击样本。
10. 因为越权和数据泄漏属于不可接受的零容忍失败。
