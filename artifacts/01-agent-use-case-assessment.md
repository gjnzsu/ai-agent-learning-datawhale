## 1. Purpose

本 Artifact 用于在方案早期回答三个问题：

1. 业务问题是否值得使用 AI；
2. 是否真的需要 Agent 的动态决策和工具反馈循环；
3. 在银行风险边界下，应选择多高的自主等级。

核心原则：

> 选择能够实现业务目标的最简单、可控、可评估方案，而不是默认选择自主程度最高的 Agent。

## 2. Intake：先把需求改写清楚

在讨论模型或框架前，先完成以下定义：

| 项目 | 必须回答的问题 |
|---|---|
| Target user | 谁会使用系统，谁对最终结果负责？ |
| Business task | 用户真正要完成的任务是什么？ |
| Current pain point | 当前流程在哪些地方耗时、出错或依赖人工？ |
| Baseline | 当前处理时长、错误率、返工率或工单量是多少？ |
| Expected outcome | 系统要生成建议、执行操作，还是更新正式状态？ |
| Data | 需要哪些数据，敏感度和授权状态如何？ |
| Tools | 需要查询或修改哪些系统？ |
| Error impact | 错误会导致返工、客户影响、资金损失还是监管风险？ |
| Completion condition | 什么状态才算任务真正完成？ |
| Human owner | 谁审核、接管并承担最终业务责任？ |

模糊需求：

> 建设一个智能 KYC Agent，提高审查效率。

可评估需求：

> 面向 KYC Auditor，读取授权范围内的脱敏申请材料，检查材料完整性，检索当前有效制度，查询 AML 报告并生成风险提示；Auditor 负责最终判断。首期不自动审批、不修改客户或 Case 状态。

## 3. 技术形态决策

### 3.1 快速判断

```text
能否用明确且稳定的规则解决？
├─ 是 → Rule
└─ 否
   ├─ 路径和分支能否提前定义？
   │  ├─ 是 → Workflow
   │  └─ 否
   │     ├─ 是否主要是一次生成、总结、分类或问答？
   │     │  ├─ 是 → LLM Application（可包含 RAG）
   │     │  └─ 否
   │     │     └─ 是否必须依据运行时反馈动态选择行动？
   │     │        ├─ 是 → 考虑受控 Agent
   │     │        └─ 否 → 重新澄清需求
```

### 3.2 技术形态对比

| 形态 | 控制方式 | 适用特征 | 银行示例 |
|---|---|---|---|
| Rule | 确定性条件 | 逻辑稳定、结果必须确定 | 金额阈值、字段校验、权限规则 |
| Workflow | 预定义步骤与分支 | 流程稳定、节点和责任明确 | OCR → 校验 → 审批 → 归档 |
| LLM Application | 单次或有限模型调用 | 总结、分类、生成、RAG 问答 | 制度问答、会议摘要 |
| Agent | 模型与程序共同决定下一步 | 路径不能完全预设，需要多工具和反馈 | 运维诊断、复杂运营分析 |
| Hybrid | 多种形态组合 | Agent 负责规划，规则和流程负责硬控制 | KYC 审查辅助、Payment Investigation |

## 4. 场景筛选评分

每个维度使用 1～5 分。前六项表示价值与可行性，后四项表示风险；两组分数不能简单相加。

| 维度 | 1 分 | 5 分 |
|---|---|---|
| 业务价值 | 价值不清楚 | 对时间、质量或风险有显著价值 |
| 使用频率 | 偶发 | 高频且覆盖用户广 |
| 路径不确定性 | 路径固定 | 需依据反馈动态改变路径 |
| 工具协同需求 | 不需要工具 | 需多工具、多轮协同 |
| 数据可用性 | 数据不可用或未授权 | 数据完整、合法且可访问 |
| 可评估性 | 无清晰标准 | 可定义完成条件和测试集 |
| 数据敏感度 | 公开或低敏 | 客户、账户、交易等高敏数据 |
| 错误影响 | 易发现、易恢复 | 资金、客户、监管或声誉影响 |
| 操作权限 | 只生成草稿 | 修改系统或产生外部副作用 |
| 人工复核难度 | 可及时复核 | 无合适人员或无法及时复核 |

### 决策区间

| 价值与可行性 | 风险 | 建议 |
|---|---|---|
| 高 | 低 | 优先 PoC |
| 高 | 中 | 受控 PoC，限制用户、数据和工具 |
| 高 | 高 | 降低自主性，从建议辅助开始 |
| 低 | 低 | 比较传统自动化的成本收益 |
| 低 | 高 | 暂缓建设 |

## 5. 候选场景组合评估

| 场景 | 路径 | 工具需求 | 错误影响 | 推荐形态 | 建议自主等级 |
|---|---|---|---|---|---|
| 交易限额校验 | 固定 | 无或单一 | 高 | Rule | 不使用 Agent |
| 定时报表摘要 | 固定 | 固定工具 | 低至中 | Workflow + LLM | L0 |
| 制度问答 | 基本固定 | RAG | 中 | LLM + RAG | L0–L1 |
| 营销文案生成与发布 | 固定审批流 | 内容工具 | 中至高 | LLM + Workflow | L1，人工发布 |
| KYC 材料初审 | 半结构化 | 文档、制度、AML | 高 | Hybrid | L1–L2 |
| Payment Investigation | 动态 | 多个查询工具 | 高 | 受控 Agent | L1–L2 |
| 运营数据分析 | 动态 | Pandas/SQL/图表 | 中 | 受控 Agent | L2 |
| IT 运维诊断 | 动态 | 日志、指标、知识库 | 中至高 | 受控 Agent | L2，只读诊断 |
| 自动批准付款 | 动态 | 高风险写工具 | 极高 | 不采用自主 Agent | 只允许建议 |

## 6. 推荐 PoC：KYC 审查辅助 Agent

### 6.1 Value statement

帮助 KYC Auditor 在一个受控流程中完成材料检查、制度检索和风险提示，减少跨系统收集与整理时间，同时保留人工最终责任。

### 6.2 In scope

- 读取脱敏或模拟的申请材料；
- 检查材料是否完整；
- 检索当前有效的 KYC 制度；
- 查询用户有权访问的 AML 报告；
- 生成带证据引用的审核建议；
- 在证据不足、数据矛盾或风险较高时转人工；
- 保存任务、工具、版本和审批审计信息。

### 6.3 Out of scope

- 自动作出 KYC、CDD、AML 或授信最终决定；
- 自动修改客户主数据；
- 自动更新正式 Case 状态；
- 查询 Auditor 未获授权的客户或 Case；
- 将原始客户数据发送到未批准的模型或工具；
- 在没有人工确认时触发不可逆业务动作。

### 6.4 Initial success measures

| 维度 | 指标 |
|---|---|
| 业务 | Case 材料收集和初审时间下降 |
| 质量 | 材料缺失项识别率、制度引用支持率 |
| 行为 | 工具与关键参数正确率 |
| 安全 | 未授权访问、跨客户泄漏、审批绕过均为零 |
| 工程 | P95 延迟、失败率、平均 Token 成本 |
| 协作 | Auditor 复核通过率、修改率和接管率 |

具体定义和门槛将在 Week 5 Evaluation Artifact 中补充。

## 7. 自主等级决定

| 等级 | 能力 | 当前建议 |
|---|---|---|
| L0 信息提供 | 搜索和展示，不形成业务建议 | 适合制度检索 |
| L1 建议辅助 | 生成建议，人负责决定 | KYC PoC 默认等级 |
| L2 受控执行 | 调用授权的只读或低风险工具 | 可在明确策略下试点 |
| L3 审批后执行 | 人确认后触发可撤销动作 | 暂不纳入首期 |
| L4 有界自动执行 | 边界内自动产生业务动作 | 不适合当前 PoC |

## 8. Key decisions

1. KYC 场景采用 Hybrid，而不是完全自主 Agent。
2. Agent 负责规划、检索和只读工具选择；确定性规则负责权限和硬约束。
3. Workflow 负责人机审批和正式状态变更。
4. 首期采用 L1，满足条件后才评估有限 L2。
5. 正式业务系统仍是事实来源，Agent Memory 不是 System of Record。
6. PoC 只使用脱敏或模拟数据。
7. 是否升级自主等级必须以 Week 5 评估结果和风险批准为依据。

## 9. Decision checklist

- [ ] 用户、任务、责任人和完成条件已明确。
- [ ] Rule、Workflow、LLM 与 Agent 选型已经比较。
- [ ] 业务基线和期望价值可以量化。
- [ ] 数据所有者、敏感等级和合法用途已确认。
- [ ] 工具权限和副作用已识别。
- [ ] 人工审批与接管节点已确定。
- [ ] In scope 与 out of scope 已书面确认。
- [ ] 可建立代表性离线评估集。
- [ ] PoC 成功指标和停止条件已定义。
- [ ] 业务、风险、技术和平台负责人同意进入 PoC。
