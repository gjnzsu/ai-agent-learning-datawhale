## 一、本课目标

完成本课后，你应该能够：

1. 将 Agent 失败分为模型、工具、数据、策略、业务和平台故障。
2. 判断哪些错误可以重试，哪些必须停止或转人工。
3. 解释超时、重试、熔断、降级、检查点和幂等之间的关系。
4. 设计 Prompt、模型、工具、策略和 Agent 配置的版本发布流程。
5. 区分日志、指标、Trace、审计和评估。
6. 为 KYC Agent 制定可靠性与降级矩阵以及监控指标。

## 二、Agent 可靠性不等于“接口可用”

传统接口只要返回 HTTP 200，不代表 Agent 任务就成功。Agent 可能：

- 调用了错误工具。
- 使用了错误数据范围。
- 在循环中重复调用模型。
- 生成了无证据的结论。
- 达到成本上限后仍未完成目标。
- 工具执行成功，但 Runtime 没有保存结果。
- 输出报告完成，但没有进入人工审批。

因此 Agent 的可靠性至少包含四层：

```text
基础设施可靠：服务、网络和存储可用
执行可靠：状态、重试、恢复和幂等正确
任务可靠：流程到达正确完成或安全停止状态
业务可靠：输出满足证据、权限和业务验收要求
```

## 三、先给失败分类

如果所有失败都返回 `AGENT_ERROR`，团队无法制定正确的恢复策略。

| 失败类型 | 示例 | 典型处理 |
| --- | --- | --- |
| 模型失败 | 超时、限流、服务不可用 | 有限重试、切换批准模型、降级 |
| 工具技术失败 | 网络超时、依赖服务 503 | 查询执行状态、有限重试、熔断 |
| 数据失败 | 材料缺失、字段冲突、数据过期 | 补件、重新获取、转人工 |
| 策略拒绝 | 越权、超出时间范围、禁止工具 | 立即停止，不应重试绕过 |
| 业务失败 | Case 已关闭、不满足处理前提 | 返回明确业务状态 |
| Agent 逻辑失败 | 循环、计划漂移、结构化输出无效 | 达到限制后停止、修复配置 |
| 平台故障 | 状态库不可用、消息堆积 | 故障转移、暂停接单、恢复检查点 |
| 结果不确定 | 工具可能成功但响应丢失 | 通过 `action_id` 查询，不直接重试 |

失败分类的目标不是让错误码变多，而是让系统能够采取不同且安全的处理方式。

## 四、超时设计

Agent 任务通常包含多层超时：

```text
单次模型调用超时
单次工具调用超时
一个节点的执行超时
等待人工审批超时
整个 Agent 任务超时
业务 Case 的 SLA
```

这些超时不能使用同一个数值。例如，模型调用可以等待几十秒，但人工审批可能允许几小时。

超时后需要返回明确状态：

```text
MODEL_TIMEOUT
TOOL_TIMEOUT
NODE_TIMEOUT
APPROVAL_EXPIRED
TASK_DEADLINE_EXCEEDED
```

超时表示“没有在期限内得到确定结果”，不一定表示底层操作没有执行。

## 五、重试：只重试可能自行恢复的问题

适合有限重试：

- 短暂网络失败。
- 模型或工具服务临时限流。
- 下游返回明确的可重试错误。
- 连接中断且操作具备幂等性。

不适合重试：

- 权限拒绝。
- 输入 Schema 错误。
- Case 已关闭。
- 材料缺失或数据冲突。
- 不可幂等行动的执行结果未知。
- 模型反复生成违反策略的工具请求。

推荐使用有限次数和退避：

```text
第 1 次失败 → 等待短时间
第 2 次失败 → 增加等待时间
第 3 次失败 → 停止重试，降级或转人工
```

重试预算应同时限制：

- 单个节点的次数。
- 单个工具的次数。
- 整个任务的总尝试次数。
- 总时间和总成本。

## 六、熔断：保护平台和下游系统

当 AML 系统持续失败时，如果大量 Agent 不断重试，会进一步压垮依赖系统。

```text
CLOSED：正常调用
   ↓ 连续失败达到阈值
OPEN：快速失败，不再调用下游
   ↓ 等待恢复窗口
HALF_OPEN：允许少量探测调用
   ↓ 成功则关闭，失败则重新打开
```

熔断后的业务策略可能是：

- KYC Agent 暂停涉及 AML 的任务。
- 明确标记 AML 证据不可用。
- 转入人工队列。
- 对只需 KYC 材料整理的步骤继续运行。

熔断不是把错误隐藏起来，而是快速失败并采取受控降级。

## 七、降级：降低能力，不降低控制标准

可选降级方式：

| 故障 | 可接受降级 | 不可接受做法 |
| --- | --- | --- |
| 主模型不可用 | 切换经过评估的备用模型 | 随意切换未知模型 |
| 所有模型不可用 | 仅显示原始证据或转人工 | 编造摘要 |
| AML 工具不可用 | 标记证据不完整并暂停 | 假设 AML 无风险 |
| 写工具不可用 | 保存草稿，进入人工处理 | 绕过网关直写数据库 |
| RAG 不可用 | 不提供制度结论或只显示缓存证据 | 无引用回答制度问题 |
| 审批服务不可用 | 暂停高风险行动 | 默认批准 |

核心原则：

```text
可以从自动化降级为人工处理
可以从执行模式降级为建议模式
不能从受控模式降级为无控制模式
```

## 八、检查点与恢复

长任务应在稳定边界保存检查点，例如：

- 一个工具节点成功之后。
- 进入人工审批之前。
- 一个计划阶段完成之后。
- 外部副作用执行并确认之后。

检查点至少记录：

```text
task_id、case_id、当前节点
配置和 Prompt 版本
已完成步骤及结果引用
待执行行动及 action_id
重试计数和预算
审批状态
最近一次可靠状态
```

恢复时不能简单地从代码行继续，而要重新确认：

- 配置版本是否仍然可用。
- 权限和 Case 状态是否变化。
- 外部行动是否已经执行。
- 待处理消息是否重复。
- 恢复是否会重复副作用。

## 九、幂等和执行结果不确定

以通知发送为例：

```text
Tool Gateway 发出请求
→ 通知系统发送成功
→ 返回途中网络中断
→ Runtime 看到 TIMEOUT
```

此时不能直接重试。正确流程是：

```text
使用 action_id 查询执行状态
├─ SUCCESS：返回原结果
├─ NOT_FOUND：在策略允许时重试
└─ UNKNOWN：暂停并转人工核查
```

对于资金、账户限制等高影响操作，执行结果不确定必须进入专门的核对和补偿流程。

## 十、并发与一致性

同一个 KYC Case 可能同时存在：

- Auditor 手工更新材料状态。
- Agent 正在读取旧状态。
- 客户刚上传新材料。
- 另一个 Agent 任务准备发送补件通知。

需要考虑：

- 业务对象版本号或乐观锁。
- 写入前重新读取关键状态。
- 一个 Case 是否允许多个写任务并行。
- 事件重复、乱序和延迟。
- 任务取消后，未处理消息如何失效。

审批绑定的参数和 Case 版本变化后，旧审批应失效。

## 十一、发布物不是只有代码

一个 Agent 版本可能由以下内容共同决定：

```text
Agent 代码版本
流程图或状态图版本
System Prompt 与模板版本
模型及模型参数
工具 Schema 和 Adapter 版本
Policy 规则版本
RAG 知识快照或索引版本
输出 Schema
评测集与通过阈值
```

建议将它们组合成可追溯的发布清单：

```json
{
  "agent_release": "kyc-agent-0.4.0",
  "code": "git-sha-1234",
  "prompt": "kyc-summary-v7",
  "workflow": "kyc-review-v4",
  "model_policy": "model-route-v3",
  "tool_contract": "kyc-tools-v5",
  "policy": "kyc-policy-v12",
  "evaluation": "kyc-regression-2026-09"
}
```

## 十二、环境隔离

至少区分开发、测试和生产环境：

| 环境 | 数据 | 工具权限 | 目的 |
| --- | --- | --- | --- |
| 开发 | 合成或脱敏数据 | Mock、只读测试工具 | 快速开发 |
| 测试/UAT | 受控测试数据 | 沙箱工具 | 集成与业务验收 |
| 生产 | 正式授权数据 | 严格白名单 | 真实业务运行 |

不应让测试 Agent 使用生产写工具，也不应将生产客户数据随意复制到开发环境。

## 十三、发布流程

```text
1. 冻结发布清单
2. 运行离线评测和回归测试
3. 安全、权限和工具契约检查
4. 业务 UAT 与人工审批流程测试
5. 小范围影子运行或只读运行
6. 灰度到低风险用户或 Case
7. 观察质量、延迟、错误、成本和人工推翻率
8. 扩大流量或触发回退
9. 完整记录发布决定
```

### 影子运行

Agent 接收真实请求副本并生成结果，但不向业务用户展示，也不执行外部动作。它适合比较新旧版本，但仍需遵守数据访问要求。

### 灰度发布

仅让部分用户、网点、Case 类型或低风险流程使用新版本。灰度单位必须可识别、可监控、可停止。

### 回退

回退不只是部署旧代码。还要考虑：

- 新旧 Prompt 和输出 Schema 是否兼容。
- 正在运行的任务继续旧版本还是迁移。
- 新工具已经产生的副作用能否撤销。
- 新版本写入的状态旧版本能否读取。

## 十四、日志、指标、Trace、审计和评估

| 类型 | 回答的问题 | 示例 |
| --- | --- | --- |
| 日志 Log | 某个组件发生了什么？ | 工具返回 503 |
| 指标 Metric | 系统整体趋势怎样？ | 工具成功率 97% |
| 链路 Trace | 一次任务经过了哪些组件？ | Runtime → Model → Tool |
| 审计 Audit | 谁基于什么权限做了什么？ | Auditor 批准通知 |
| 评估 Evaluation | Agent 输出和行为质量如何？ | 引用正确率、任务完成率 |

它们不能互相替代。例如 Trace 可以显示模型被调用了，但不代表输出符合 KYC 质量标准；普通日志也不一定满足审计的防篡改和保留要求。

## 十五、Agent 的关键观测对象

一次 Trace 可以包含：

```text
Task Span
├─ Policy Check Span
├─ Tool Call Span: kyc.get_documents
├─ Tool Call Span: aml.get_summary
├─ Model Call Span: generate_summary
├─ Reflection Span
├─ HITL Wait Span
└─ Tool Call Span: notification.send
```

Span 建议关联：

- `trace_id`、`task_id`、`case_id` 的受控标识。
- Agent、Prompt、模型、工具和策略版本。
- 延迟、Token、错误类型和重试次数。
- 输入输出大小，而非无条件记录全部敏感内容。

## 十六、监控指标分层

### 平台健康

- 请求量、并发数和队列长度。
- P50、P95、P99 延迟。
- 模型和工具错误率。
- 状态存储、消息积压和熔断状态。

### Agent 执行

- 任务完成、失败、取消和转人工率。
- 平均步骤数和步数超限率。
- 模型及工具调用次数。
- 重试、恢复和重复行动次数。
- 每任务 Token、时间和成本。

### 业务质量

- 证据完整率和引用正确率。
- Auditor 修改、拒绝和推翻率。
- 材料识别准确率。
- 平均审查处理时长和返工率。

### 风险控制

- 越权调用拦截数。
- 未经审批的高风险行动数，目标应为零。
- 审批过期和错误角色审批数。
- 敏感数据策略命中数。
- 重复副作用和结果未知事件数。

## 十七、告警必须可行动

“错误率升高”不够具体。告警应包含：

- 影响哪个 Agent、租户和版本。
- 从什么时候开始。
- 影响多少任务和 Case。
- 是模型、工具、状态还是策略问题。
- 当前是否已经熔断或降级。
- 值班人员可以执行什么操作。

示例：

```text
KYC Agent 0.4.0 的 AML 工具在 10 分钟内超时率达到 25%；
熔断器已打开，42 个任务暂停在 AML_CHECK；
当前无外部写操作，建议检查 AML 服务并保持人工降级。
```

## 十八、KYC 可靠性与降级矩阵

| 故障场景 | 自动处理 | 用户可见状态 | 最终处置 |
| --- | --- | --- | --- |
| 模型限流 | 退避重试一次 | 正在重试 | 备用批准模型或转人工 |
| AML 503 | 有限重试并熔断 | AML 数据暂不可用 | 暂停相关任务 |
| 材料缺失 | 不重试 | 等待补件 | Auditor 发起补件 |
| 权限拒绝 | 不重试 | 无权访问 | 记录并终止 |
| 通知结果未知 | 查询 `action_id` | 正在核对 | 未确定则人工核查 |
| Prompt 新版质量下降 | 停止扩流 | 使用稳定版本 | 回退发布清单 |
| 审批服务不可用 | 不执行高风险行动 | 等待人工服务恢复 | 安全暂停 |

## 十九、项目经理评审清单

### 可靠性

- 失败是否分类？
- 每类失败是否明确可重试性？
- 是否有节点和任务两级预算？
- 写操作是否具备幂等或补偿方案？
- 熔断和降级是否保护业务控制？

### 发布

- 是否能还原一次运行的完整版本组合？
- 是否有隔离环境、回归评测和 UAT？
- 灰度单位和回退触发条件是否明确？
- 运行中任务如何处理版本变化？

### 可观测性

- 能否通过 `trace_id` 串联全链路？
- 指标能否区分平台健康、执行质量和业务质量？
- 是否避免无条件记录敏感输入输出？
- 告警是否包含明确处置动作？

## 二十、本课学习方式

### 第一段：可靠执行，约 40 分钟

阅读第二至第十节，重点掌握失败分类、重试、熔断、降级、检查点和幂等。

阅读第十四至十九节，区分五类观测手段并设计 KYC 指标。

## 二十一、轻量练习

1. 判断五种 KYC 故障中哪些可以重试、降级或必须转人工，并说明原因。
2. 为一个 Agent 新版本写出发布清单和三个灰度回退条件。
3. 分别写出两个平台健康指标、两个 Agent 执行指标、两个业务质量指标和两个风险控制指标。
