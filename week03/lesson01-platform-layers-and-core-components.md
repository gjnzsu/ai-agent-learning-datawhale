## 二、从一个 Agent 到 Agent 平台

### Agent 应用

面向具体用户和业务目标，例如：

- KYC 审查辅助 Agent。
- 网点运营分析 Agent。
- 制度检索助手。

它回答的是：“这个业务任务怎样完成？”

### Agent 框架

为开发者提供构建 Agent 的代码抽象，例如：

- Agent 生命周期和执行循环。
- 状态图、节点和条件边。
- 模型调用、工具调用和消息格式。
- 多 Agent 通信。

它回答的是：“开发者怎样实现 Agent？”

### Agent 平台

为多个团队和多个 Agent 应用提供共享的开发、运行及治理能力，例如：

- 模型和工具统一接入。
- 租户、身份和权限管理。
- Prompt 与配置版本管理。
- 任务状态、审批和审计。
- 监控、评估、成本与发布控制。

它回答的是：“组织怎样安全、稳定、规模化地运营 Agent？”

```text
Agent 应用使用 Agent 框架实现
Agent 应用运行在 Agent 平台之上
Agent 框架只是平台技术栈的一部分
```

选用了 LangGraph、AutoGen 或 AgentScope，并不等于已经拥有企业级 Agent 平台。

## 三、银行 Agent 平台五层模型

```text
┌─────────────────────────────────────────────┐
│ 应用层：KYC、运营分析、客服、研发与风控辅助     │
├─────────────────────────────────────────────┤
│ 编排层：Agent Runtime、Workflow、状态、HITL   │
├─────────────────────────────────────────────┤
│ 能力层：模型、工具、RAG、Prompt、记忆、评估    │
├─────────────────────────────────────────────┤
│ 治理层：身份、权限、安全、审计、成本、可观测性  │
├─────────────────────────────────────────────┤
│ 基础层：计算、模型服务、数据库、消息与 API 网关 │
└─────────────────────────────────────────────┘
```

这个图表示逻辑职责，而不一定对应五套独立系统。治理能力通常横切每一层。

## 四、应用层：业务责任留在业务应用

应用层负责：

- 定义目标用户、业务目标和 Case 类型。
- 配置业务步骤和输入输出。
- 定义何时完成、何时转人工。
- 展示证据、建议和审批界面。
- 承担业务验收和运营结果。

KYC 应用应知道“受益所有人材料是否必需”，但通用平台不应该硬编码所有 KYC 规则。

边界原则：

```text
通用能力进入平台
场景特有规则留在业务域
```

否则平台会逐渐包含各业务条线的特殊逻辑，任何变更都需要修改公共底座。

## 五、编排层：Agent Runtime 是执行中枢

Agent Runtime 负责运行任务，而不负责自行突破治理规则。典型职责包括：

- 接收目标和上下文，创建任务实例。
- 运行 ReAct、Plan-and-Solve 或固定 Workflow。
- 维护当前节点、步骤、循环和停止条件。
- 调用模型与工具，但不直接保存密钥。
- 暂停任务、保存检查点并等待人工。
- 处理超时、取消、重试和恢复。
- 发送运行事件供监控和审计使用。

Runtime 需要回答：

```text
任务现在运行到哪里？
为什么走到这个分支？
下一步是否允许执行？
失败后能否恢复？
何时应该停止？
```

### Workflow 与 Agent 可以共存

```text
外层：确定性 Workflow 控制关键阶段
内层：Agent 在授权范围内动态分析
```

例如：

```text
创建 KYC Case
→ 材料完整性规则检查
→ Agent 动态整理冲突和风险
→ 确定性合规校验
→ Auditor 人工复核
→ 正式系统更新结果
```

银行平台通常不需要把所有流程都改造成自主 Agent。

## 六、模型网关：统一管理模型调用

业务 Agent 不应分别保存供应商密钥并直接调用模型。模型网关可以提供：

- 统一 API 和身份认证。
- 模型白名单与访问权限。
- 模型路由和版本固定。
- Token、并发、速率和预算限制。
- 超时、重试、熔断与降级。
- 敏感数据策略和调用审计。
- 使用量、延迟、错误率和成本统计。

模型路由示例：

```text
普通摘要 → 成本较低的内部批准模型
复杂分析 → 能力更强的批准模型
敏感数据 → 仅允许指定部署区域或本地模型
主模型不可用 → 降级为只读检索或转人工
```

模型网关不应承担业务事实判断。它负责“用哪个模型、能不能调用、怎样可靠调用”，而不是决定客户是否通过 KYC。

## 七、工具网关：隔离 Agent 与业务系统

如果 Agent 直接连接 KYC、AML、核心银行和通知系统，会出现：

- 权限分散，难以统一撤销。
- 每个 Agent 重复实现鉴权和审计。
- 工具参数缺少统一约束。
- 底层接口变化影响大量 Agent。
- 无法集中禁用高风险操作。

工具网关或工具服务层可以负责：

- 工具注册、版本、描述与所有者。
- 调用方身份、用户身份和 Case 权限校验。
- 输入 Schema 校验和参数范围限制。
- 读写分级以及审批策略。
- 超时、有限重试、熔断和限流。
- 幂等键、执行状态查询和结果标准化。
- 脱敏、日志和审计事件。
- 工具停用与紧急开关。

```text
Agent 选择工具
→ Policy 判断是否允许及是否需要审批
→ Tool Gateway 校验身份与参数
→ Adapter 调用真实业务系统
→ 标准化结果返回 Runtime
```

工具描述告诉模型“这个工具能做什么”，但真正的权限必须在运行时强制执行。

## 八、Prompt 与配置管理

生产环境中的 Prompt 不只是一段文字。它还可能包含：

- System Prompt 和模板变量。
- 可使用的工具集合。
- 模型与参数配置。
- 输出 Schema。
- 最大步数、时间和成本限制。
- 评审规则和人工介入条件。

建议具备：

- 版本号和变更记录。
- 开发、测试、生产环境隔离。
- 审批、灰度和快速回退。
- Prompt 与 Agent、模型、评测集的关联。
- 密钥与普通配置分离。

一次运行应能追溯到确切的 Prompt 和配置版本，而不是只记录“使用了最新版本”。

## 九、会话状态与任务状态不是一回事

### 会话状态

服务于连续交互，例如：

- 用户刚才问过什么。
- 当前话题和界面上下文。
- 对话中的临时偏好。

### 任务状态

服务于业务任务可靠执行，例如：

- `task_id`、`case_id` 和当前节点。
- 已完成步骤及工具结果。
- 待审批行动和版本。
- 重试次数、预算和截止时间。
- 完成、失败、取消或转人工状态。

```text
用户可以关闭对话页面，任务仍在后台等待审批；
用户也可以开始新会话，继续处理同一个 Case。
```

因此不能只把聊天记录当作任务数据库。正式业务状态仍应保存在权威业务系统中，Agent 状态存储保存的是执行过程和恢复信息。

## 十、消息与事件：让组件解耦

同步调用适合需要立即返回的短链路：

```text
应用 → Runtime → 模型网关 → 返回结果
```

异步消息适合长任务和多个消费者：

```text
Runtime 发布 TASK_WAITING_APPROVAL
→ 审批服务创建待办
→ 通知服务提醒 Auditor
→ 审计服务记录事件
→ 监控服务计算等待时长
```

消息驱动有利于解耦和恢复，但也带来重复消息、乱序、最终一致性和排错复杂度。事件应包含唯一 ID、任务 ID、时间、版本和幂等信息。

## 十一、治理层：横切所有组件

治理层不是上线前最后加的一组检查，而应贯穿请求链路：

| 治理能力 | 关键问题 |
| --- | --- |
| 身份认证 | 当前用户、应用和服务是谁？ |
| 权限策略 | 能访问哪个 Case、字段、模型和工具？ |
| 数据安全 | 输入输出是否需要脱敏、过滤或阻断？ |
| 审计 | 能否还原模型、工具、参数、证据和人工决定？ |
| 可观测性 | 哪个节点慢、贵、失败或进入循环？ |
| 成本治理 | 谁使用了多少模型和工具资源？ |
| 评估 | 新版本是否达到上线门槛？ |
| 发布治理 | 能否灰度、暂停和回退？ |

治理规则应由确定性系统执行，不能只写在 Prompt 中要求模型自觉遵守。

## 十二、基础层：平台依赖的工程底座

基础层可能包括：

- Kubernetes、虚拟机或其他计算环境。
- 模型推理服务和 GPU 资源。
- 关系数据库、对象存储、缓存和向量库。
- 消息队列、服务注册和 API 网关。
- 密钥管理、日志、指标和链路追踪系统。

项目经理不必掌握每个基础设施的配置，但需要明确：

- 谁负责容量和可用性？
- 数据存在哪里、保留多久？
- 故障时的降级模式是什么？
- 哪些系统是单点依赖？
- 恢复时间和数据恢复目标是什么？

## 十三、KYC Agent 的端到端请求链路

```text
1. Auditor 在 KYC 应用发起 Case 分析
2. API Gateway 验证用户与应用身份
3. Policy Service 校验 Agent 启动权限与 Case 访问范围
4. Agent Runtime 创建 task_id 并加载已发布配置
5. Runtime 根据流程或模型建议构造结构化工具请求
6. Policy Service 判断具体工具、数据范围和参数是否允许
7. Tool Gateway 再次校验调用身份、工具白名单和参数
8. Tool Gateway 通过 Adapter 调用 KYC、AML 等业务系统
9. Adapter 标准化结果，记录来源与版本并返回 Runtime
10. Runtime 校验、保存并整理工具返回的 Observation
11. Runtime 构造模型上下文，通过 Model Gateway 调用模型
12. Model Gateway 将模型结果返回 Runtime
13. Runtime 解析模型结果，并执行规则与证据检查
14. 模型提出补件建议，Runtime 不直接执行外部行动
15. Policy Service 判定发送通知需要 Auditor 审批
16. Runtime 保存检查点并发布待审批事件
17. Auditor 审批后，平台再次校验身份、参数和 Case 状态
18. Tool Gateway 使用 action_id 幂等发送通知
19. 工具执行结果返回 Runtime，Runtime 更新任务状态
20. 全链路日志、指标和审计事件关联同一 trace_id
```

### 两阶段权限检查

权限检查不是在工具尚未确定时预先批准所有调用，而是分为两个阶段：

| 阶段 | 已知信息 | 主要判断 |
| --- | --- | --- |
| 任务入口授权 | 用户、角色、Agent、`case_id` 和业务目的 | 能否启动该 Agent，并访问这个 Case |
| 具体行动授权 | 工具、字段、时间范围、参数和目标资源 | 能否执行这一次精确的工具调用 |

入口授权建立本次任务的授权上下文；等 Runtime 构造出具体工具请求后，Policy Service 才能进行细粒度授权。Tool Gateway 随后在真实执行边界再次强制校验。

```text
Policy Service：决定允许什么
Tool Gateway：保证只执行被允许的内容
```

### 工具结果不能直接跳到模型调用

业务系统返回结果后，Runtime 需要先把它作为 Observation 处理：

- 判断工具调用成功、失败还是只返回部分数据。
- 将结果关联到当前 `task_id`、节点和工具调用。
- 检查数据来源、版本、完整性和后续步骤前提。
- 根据错误类型选择有限重试、降级、重新规划或转人工。
- 只将经过授权和整理的信息放入模型上下文。

例如 KYC 查询成功而 AML 查询超时，Runtime 不应直接要求模型生成完整结论。它应先按照策略重试；仍然失败时，应标记证据不完整并安全停止或转人工。

可以使用四个标识区分不同范围：

| 标识 | 作用 |
| --- | --- |
| `case_id` | 对应业务 Case |
| `task_id` | 对应一次 Agent 任务 |
| `trace_id` | 串联一次分布式请求链路 |
| `action_id` | 保证具体外部行动可追踪且幂等 |

## 十四、常见架构误区

### 误区 1：一个服务承担所有职责

Agent 服务同时保存密钥、判断权限、调用业务库、执行审批和记录审计，会难以隔离风险，也难以独立升级。

### 误区 2：所有能力都立即建设成平台

PoC 尚未证明价值时就建设完整多租户平台，可能造成高成本和低使用率。先识别可以被多个场景复用的最小能力。

### 误区 3：把治理规则写进 Prompt

“请不要访问无权限数据”不是技术权限控制。权限必须由网关和策略服务强制执行。

### 误区 4：聊天记录就是全部状态

聊天历史无法可靠表达业务状态、审批版本和工具副作用，也不应替代权威业务系统。

### 误区 5：框架选型等于平台架构

框架解决部分编排和开发问题；身份、权限、审计、发布、成本和运营通常仍需要平台设计。

### 误区 6：组件越多越先进

每增加一个服务都会带来部署、网络、版本、一致性和运维成本。组件边界应来自真实的安全、扩展或组织需求。

## 十五、平台项目经理的组件卡片

评审每个组件时，可以统一询问：

```text
组件名称：
核心职责：
明确不负责什么：
上游与下游：
同步接口与异步事件：
输入输出 Schema：
身份与权限：
超时、重试、幂等和降级：
状态与数据所有权：
日志、指标和审计：
负责人及 SLA：
```

“不负责什么”尤其重要，它可以帮助团队发现职责重叠。

## 十六、概念接口示例

Java 业务系统可以调用 Python Agent 服务暴露的稳定 API，而不依赖 Python 内部框架类型：

```http
POST /v1/agent-tasks
Authorization: Bearer <service-token>
Idempotency-Key: <request-id>
Content-Type: application/json
```

```json
{
  "agent_id": "kyc-review-assistant",
  "case_id": "KYC-2026-00128",
  "requested_by": "auditor-008",
  "goal": "生成带证据来源的 KYC 审查辅助摘要"
}
```

```json
{
  "task_id": "TASK-1001",
  "status": "QUEUED",
  "configuration_version": "kyc-agent-0.3"
}
```

长任务可以通过查询接口或事件通知获得进展，避免保持一个超长 HTTP 连接。具体集成方式将在第三课展开。
