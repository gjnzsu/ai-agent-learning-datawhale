## 一、本课目标

完成本课后，你应该能够：

1. 将银行 AI 需求归类为传统规则、Workflow、LLM 应用或 Agent。
2. 从业务价值、任务不确定性、数据风险和操作风险评估场景。
3. 识别“为了使用 Agent 而使用 Agent”的伪需求。
4. 为场景选择合理的自主等级和人工复核机制。
5. 给出继续调研、开展 PoC、降级为 Workflow 或暂缓建设的建议。

本课不追求找到技术上最先进的方案，而是训练选择**最简单、可控且足以实现业务目标的方案**。

## 二、项目经理首先要问的问题

收到“希望建设一个智能 Agent”的需求时，先不要讨论框架和模型。依次确认：

1. **用户是谁？** 一线员工、运营人员、客户经理、风险人员，还是外部客户？
2. **要完成什么任务？** 使用动词描述，不使用“智能化赋能”之类抽象表述。
3. **现有流程的问题是什么？** 时间长、人员不足、错误多、知识分散，还是体验不好？
4. **成功如何衡量？** 节省时间、提高准确率、降低转人工率，还是提高制度检索命中率？
5. **错误会造成什么后果？** 低影响建议、内部返工、客户投诉、资金损失或监管风险？
6. **系统需要访问或改变什么？** 文档、客户信息、账户数据、审批状态还是交易状态？
7. **是否真的需要动态决策？** 如果步骤和分支都能提前定义，Workflow 可能更合适。

### 把模糊需求改写成可评估需求

模糊表述：

> 建设一个智能信贷 Agent，提高审批效率。

更适合评估的表述：

> 面向信贷审查人员，读取脱敏申请材料，检查材料完整性，检索相关制度，生成缺失项和风险提示，由审查人员确认；首期不自动作出授信决策，也不修改业务系统数据。

改写后，用户、输入、任务、输出、权限和边界都更加明确。

## 三、四种技术形态如何选择

### 1. 传统规则

适合条件：

- 判断条件明确且稳定。
- 需要结果完全确定、可解释和可审计。
- 错误影响高，不适合概率性输出。

银行示例：

- 必填字段校验。
- 金额阈值判断。
- 黑白名单精确匹配。
- 权限和交易限额控制。

### 2. Workflow

适合条件：

- 步骤和分支可以提前设计。
- 需要稳定执行、明确 SLA 和完整审计。
- LLM 只是某些节点的文本处理能力。

银行示例：

- 材料上传 → OCR → 字段校验 → 人工复核 → 归档。
- 投诉分类 → 摘要生成 → 按类别分派工单。
- 营销文案生成 → 敏感词检查 → 合规审批 → 发布。

### 3. 普通 LLM 应用

适合条件：

- 主要任务是生成、改写、总结、分类或问答。
- 不需要自主规划和多轮工具调用。
- 输出可以由人复核，或者错误影响较低。

银行示例：

- 会议纪要摘要。
- 内部邮件润色。
- 制度文档问答。
- 客户经理话术建议。

制度问答若包含检索，通常仍可视为带 RAG 的 LLM 应用，不必因此称为 Agent。

### 4. Agent

适合条件：

- 任务目标明确，但解决路径难以提前完整枚举。
- 下一步行动需要依据运行时反馈动态决定。
- 需要在多个工具之间选择、组合并调整行动。
- 有明确的停止条件、失败处理和权限边界。

银行示例：

- IT 运维诊断助手：根据日志和监控结果选择后续诊断工具。
- 运营分析助手：根据初步数据发现继续选择分析维度。
- 复杂制度研究助手：检索多个制度来源，判断证据是否充分并补充检索。

## 四、快速判断决策树

```text
需求是否能用明确、稳定的规则解决？
├─ 是 → 传统规则
└─ 否
   │
   ├─ 执行步骤和分支能否提前定义？
   │  ├─ 是 → Workflow
   │  └─ 否
   │     │
   │     ├─ 是否主要是一次生成、总结、分类或问答？
   │     │  ├─ 是 → 普通 LLM 应用
   │     │  └─ 否
   │     │     │
   │     │     └─ 是否需要依据工具反馈动态选择行动？
   │     │        ├─ 是 → 考虑 Agent
   │     │        └─ 否 → 重新澄清需求或采用 Workflow
```

“适合 Agent”只表示技术形态可能匹配，还必须继续做价值和风险评估。

## 五、银行 Agent 场景筛选表

建议每项使用 1～5 分：1 表示低，5 表示高。

| 维度 | 核心问题 | 高分含义 |
|---|---|---|
| 业务价值 | 能否明显节省时间、提高质量或解决关键痛点？ | 价值高且可量化 |
| 使用频率 | 任务发生得是否足够频繁？ | 高频、用户覆盖广 |
| 路径不确定性 | 是否需要根据中间结果决定下一步？ | 很难预设完整路径 |
| 工具协同需求 | 是否需要动态选择多个工具？ | 多工具、多轮调用 |
| 数据可用性 | 是否有合法、完整、可访问的数据？ | 数据质量好且已授权 |
| 可评估性 | 是否能建立标准答案或明确评价标准？ | 容易构建测试集 |
| 数据敏感度 | 是否涉及个人、账户、交易或内部敏感信息？ | 敏感度高，风险更高 |
| 错误影响 | 错误是否导致资金、客户、合规或声誉损失？ | 后果严重 |
| 操作权限 | 是否会修改系统或触发外部行动？ | 写操作或高权限操作多 |
| 人工复核 | 是否有合适人员及时检查输出？ | 难以安排人工复核 |

注意：前六项大体反映“价值与可行性”，后四项反映“风险”。不能把所有分数简单相加后机械决策。

### 建议的初步决策

| 价值/可行性 | 风险 | 建议 |
|---|---|---|
| 高 | 低 | 优先开展 PoC |
| 高 | 中 | 受控 PoC，限定数据、工具和用户 |
| 高 | 高 | 先降级为辅助模式，并完成风险论证 |
| 低 | 低 | 比较传统自动化是否更经济 |
| 低 | 高 | 暂缓建设 |

## 六、自主等级与控制策略

Agent 并非只有“自动”和“不自动”两种状态。

| 等级 | 系统能力 | 银行场景建议 |
|---|---|---|
| L0 信息提供 | 只检索和展示信息 | 可用于制度检索，但必须显示来源 |
| L1 建议辅助 | 生成建议，不执行操作 | 适合客户经理、审查和运营辅助 |
| L2 受控执行 | 调用只读或低风险工具 | 记录轨迹，对关键结果人工确认 |
| L3 审批后执行 | 生成行动方案，经人确认后执行 | 适合工单创建等可撤销操作 |
| L4 有界自动执行 | 在严格边界内自动操作 | 仅适合低风险、高可监控任务 |

对授信决策、反洗钱处置、客户权益、资金交易等高影响场景，应优先采用辅助决策和人工复核，避免让模型独立作出最终决定。

### 最小权限原则

- 首期 PoC 尽量只使用脱敏或模拟数据。
- 工具默认只读，写操作单独授权。
- 每个工具限定调用者、数据范围、参数范围和调用频率。
- 高风险动作必须二次确认。
- 保存模型版本、Prompt 版本、输入摘要、工具参数、结果和审批人。

## 七、六个银行场景示例

### 场景 1：交易限额校验

- 推荐：传统规则。
- 理由：条件明确，必须确定执行，不需要语言模型。
- 常见误区：为了体现“智能”而让 LLM 判断数值阈值。

### 场景 2：营销文案生成与发布

- 推荐：LLM 应用 + Workflow。
- 流程：生成文案 → 敏感词与规则检查 → 合规审核 → 人工发布。
- 不建议首期使用 Agent 自主发布。

### 场景 3：制度问答助手

- 推荐：RAG 型 LLM 应用。
- 要求：答案带出处、按用户权限检索、过期制度及时下线。
- 只有当系统需要跨来源研究并根据证据动态补充检索时，才考虑 Agent。

### 场景 4：信贷材料初审辅助

- 推荐：规则 + Workflow + LLM 的组合。
- 规则检查必填项，OCR/模型提取非结构化信息，Workflow 编排人工复核。
- 首期不建议让 Agent 自动作出授信决定。

### 场景 5：运营数据分析助手

- 推荐：受控 Agent PoC。
- 理由：分析路径可能随中间结果改变，需要动态选择分析维度和工具。
- 控制：只读数据、受限分析函数、结果校验、结论标注证据。

### 场景 6：IT 运维故障诊断

- 推荐：从只读诊断 Agent 开始。
- Agent 可查询日志、指标和知识库，但首期只给出诊断与修复建议。
- 重启服务、修改配置等动作必须审批并审计。

## 八、常见伪 Agent 需求

### 1. “领导要求使用 Agent”

技术名词不是业务目标。应重新确认问题、用户和衡量指标。

### 2. “流程有十几个步骤，所以需要 Agent”

步骤多不代表路径不确定。固定的复杂流程仍然属于 Workflow。

### 3. “接入知识库，所以是 Agent”

一次检索加回答通常是 RAG 应用，不一定需要 Agent 循环。

### 4. “希望完全替代人工”

先评估错误后果、责任主体和异常处理。高风险场景通常应从辅助模式开始。

### 5. “先建设通用 Agent 平台，再寻找场景”

平台能力应由代表性场景验证，否则容易形成能力很多、业务采用率很低的平台。

## 十、分类题参考答案

1. **规则**：证件日期比较明确且需要确定性结果。
2. **LLM 应用**：主要是对一次输入进行摘要生成。
3. **Workflow**：审批路径和节点预先确定。
4. **Agent**：需要根据每轮诊断反馈选择后续工具，但首期应限制为只读诊断。
5. **RAG 型 LLM 应用**：检索并回答即可；如果需要跨来源动态研究，再考虑 Agent。
6. **Agent**：分析路径会根据中间结果变化，需要动态选择分析工具和维度。

实际项目可能采用组合架构。例如，Agent 负责规划和选择工具，Workflow 负责审批，规则引擎负责硬约束，LLM 负责文本理解和解释。
