## 二、RAG 解决什么问题

RAG 是 Retrieval-Augmented Generation，即检索增强生成。

```text
用户问题
   ↓
从知识库检索相关内容
   ↓
把相关内容放入模型上下文
   ↓
模型根据证据生成答案
```

它主要解决：

- 模型不知道银行内部制度。
- 模型预训练知识可能已经过时。
- 回答需要展示原文依据。
- 不同部门只能访问不同知识。
- 制度更新后需要及时生效，而不必重新训练模型。

RAG 不保证答案正确。它可能检索错、漏检、引用过期文档，模型也可能曲解检索结果。

## 三、RAG 与其他概念的区别

### 模型参数知识

来自预训练或微调，存在模型参数中。它适合通用语言能力，但难以实时更新，也难以准确追溯到内部制度原文。

### 普通关键词搜索

主要根据关键词匹配返回文档。它可以独立使用，也可以成为 RAG 的一种检索通道。

### RAG

先检索外部证据，再让模型基于证据生成回答。重点是“检索 + 上下文 + 生成”。

### Agent Memory

保存用户、会话或任务历史，例如“这个 Auditor 上一轮正在处理哪个 Case”。它不是权威制度库，也不应覆盖正式制度。

```text
制度库回答：规则是什么？
业务系统回答：Case 的事实是什么？
Memory 回答：之前发生或讨论过什么？
```

## 四、银行制度 RAG 的两条链路

### 离线知识处理链路

```text
制度源接入
→ 文件解析与 OCR
→ 结构和质量检查
→ 元数据补充
→ 文档切分
→ Embedding
→ 建立关键词与向量索引
→ 发布知识版本
```

### 在线问答链路

```text
用户提问与身份上下文
→ 问题理解
→ 权限与知识范围计算
→ 在允许范围内检索
→ 重排与证据校验
→ 构建模型上下文
→ 生成带引用的答案
→ 输出校验、审计与反馈
```

离线链路决定“知识库里有什么”；在线链路决定“本次用户能看到什么，以及模型如何使用它”。

## 五、知识源接入

银行知识可能来自：

- 总行和分行制度库。
- 合规通知和操作规程。
- 产品手册与业务 FAQ。
- 已批准的培训材料。
- 监管文件及其内部解释。

每类知识源应明确：

```text
文档所有者
权威来源系统
允许使用的业务目的
密级和可见范围
发布日期、生效日和失效日
版本及替代关系
更新频率
撤回和纠错负责人
```

不要把共享盘里的所有文件直接批量导入生产知识库。草稿、重复版本和个人笔记可能污染答案。

## 六、解析与质量检查

PDF、Word、网页和扫描件需要转换成可处理文本。解析时应保留：

- 标题和章节层级。
- 表格行列关系。
- 页码、条款号和附件关系。
- 脚注和例外条件。
- 文档及段落来源标识。

常见质量问题：

- OCR 将金额、日期或条款号识别错误。
- 页眉页脚混入正文。
- 表格被拆成无意义的文本顺序。
- 附件与主制度失去关联。
- 同一文档被重复接入。
- 解析后缺少关键章节。

应在建立索引前执行完整性、格式和抽样校验。

## 七、元数据是治理基础

每个文档和 Chunk 不应只有正文，还应携带元数据：

```json
{
  "document_id": "KYC-POLICY-2026-03",
  "document_version": "3.0",
  "title": "企业客户 KYC 审查管理办法",
  "section": "4.2 受益所有人材料",
  "owner_department": "COMPLIANCE",
  "classification": "INTERNAL_CONFIDENTIAL",
  "allowed_roles": ["KYC_AUDITOR"],
  "allowed_orgs": ["HEAD_OFFICE", "BRANCH_A"],
  "published_at": "2026-08-20",
  "effective_from": "2026-09-01",
  "effective_to": null,
  "status": "ACTIVE",
  "source_uri": "policy://KYC-POLICY-2026-03",
  "page": 18,
  "content_hash": "..."
}
```

没有这些元数据，就很难实现权限过滤、版本选择、引用和知识撤回。

## 八、文档切分不是按固定字数切开

Chunk 是进入检索索引的内容单元。Chunk 太大：

- 混入多个主题。
- 召回内容不够精确。
- 占用更多 Token。

Chunk 太小：

- 条款上下文丢失。
- 例外条件与主规则分离。
- 模型难以理解完整含义。

银行制度更适合优先依据结构切分：

```text
制度 → 章 → 节 → 条款 → 条款内段落
```

切分时需要保留：

- 父级标题路径。
- 条款编号。
- 相邻上下文或父 Chunk 引用。
- 表格整体关系。
- 主规则与例外条款的关联。

固定 Token 长度可以作为约束，但不应破坏业务语义。

## 九、Embedding 与向量检索

Embedding 将文本转换为向量，使语义相近的内容在向量空间中更接近。

例如用户问：

> 企业客户实际控制人资料过期怎么办？

即使制度使用的是“受益所有人证明失效”，语义检索仍可能找到相关条款。

需要记录：

- Embedding 模型和版本。
- 向量维度和距离算法。
- 索引构建时间。
- 文档版本和 Chunk 版本。
- 模型升级后的重建计划。

更换 Embedding 模型通常需要重新生成向量并验证检索质量，不能直接混用不同向量空间。

## 十、混合检索

向量检索擅长语义相似，但精确编号、产品代码和专有名词可能更适合关键词搜索。

```text
关键词检索：精确命中“第 4.2 条”“KYC-103”
向量检索：理解“实际控制人资料过期怎么办”
```

混合检索可以合并两类结果，再统一重排。

不要默认“向量数据库就是 RAG”。向量库只是检索链路的一个组件。

## 十一、先权限过滤，再语义检索

危险方式：

```text
先从全部文档中检索 Top 20
→ 再删除用户无权查看的结果
```

问题包括：

- 检索系统已经处理了越权内容。
- 无权文档可能影响查询改写和排序。
- 过滤后没有足够结果，系统可能错误降级。
- 调试日志或缓存可能泄露越权内容。

推荐逻辑：

```text
认证用户与应用
→ 计算部门、角色、机构、Case 和业务目的
→ 形成允许的知识范围
→ 在允许范围内执行关键词与向量检索
→ 对返回结果再次做权限校验
```

这相当于“检索前约束 + 返回前复核”。

## 十二、权限不是只有角色

银行知识权限可能同时依赖：

- 用户角色。
- 所属部门和机构。
- 文档密级。
- 当前业务目的。
- 是否参与当前 Case。
- 地区、产品和法人实体。
- 生效时间和特殊授权。

```text
可以访问 KYC 制度
≠
可以访问所有客户 Case
```

制度知识权限和客户业务数据权限是两套不同控制，构建上下文时两者都必须满足。

## 十三、检索、重排与证据集合

第一阶段检索通常追求召回率，返回较多候选；重排阶段再根据问题相关性和业务条件选择最有价值的证据。

重排需要考虑：

- 与问题的语义相关性。
- 文档权威级别。
- 当前是否生效。
- 总行与分行制度的适用关系。
- 主规则与例外条款是否完整。
- 是否存在更新版本。
- 内容是否重复或相互冲突。

最终上下文不应只取相似度最高的一个 Chunk，而忽略必要的定义和例外条款。

## 十四、构建模型上下文

建议将上下文明确分区：

```text
[系统职责与禁止事项]
[用户问题]
[用户与业务范围]
[经过权限过滤的制度证据]
[相关 Case 事实]
[输出格式和引用要求]
```

制度证据和 Case 事实必须区分。模型不应把“制度要求提交材料”误写成“该客户已经提交材料”。

只放入回答当前问题所需的最少内容，以降低成本、干扰和敏感数据暴露。

## 十五、带引用的答案

一个可用答案应将主要结论绑定到证据：

```text
结论：企业客户的受益所有人证明已失效时，应请求更新材料，
在资料齐备前不应直接形成最终通过结论。

依据：
- 《企业客户 KYC 审查管理办法》3.0，第 4.2 条，第 18 页
- 生效日期：2026-09-01
```

引用应包含稳定标识，而不只是文档标题：

- `document_id` 和版本。
- 条款或章节。
- 页码或原文位置。
- 来源系统链接。
- 生效状态和检索时间。

## 十六、引用校验

模型生成引用后，需要验证：

- 引用的文档是否真实存在。
- 用户是否有权查看该引用。
- 文档版本是否仍然生效。
- 引用段落是否支持对应结论。
- 链接是否指向正确位置。
- 模型是否把两个来源拼成不存在的条款。

前四项应尽量由检索记录、规则和程序完成，不能完全依赖模型自我检查。

## 十七、知识版本与生效时间

制度生命周期可以包含：

```text
DRAFT → APPROVED → PUBLISHED → ACTIVE
                            ↓
                    SUPERSEDED / REVOKED
```

需要区分：

- 发布日期：文档何时公布。
- 生效日期：从何时开始适用。
- 失效日期：从何时不再适用。
- 替代关系：哪个新版本替代旧版本。

回答“当前规则是什么”时只使用当前生效版本；回答历史 Case 时，可能需要使用业务发生当时有效的版本。

## 十八、知识更新与失效

当制度更新或撤回时，需要：

```text
接收权威源变更事件
→ 校验新版本和元数据
→ 解析、切分、Embedding 与索引
→ 通过检索回归测试
→ 原子切换到新知识版本
→ 将旧版本标记为被替代
→ 清理或失效相关缓存
→ 记录发布时间和影响范围
```

如果发现某文档错误：

- 可以立即从在线检索范围撤回。
- 找出哪些答案曾引用该文档。
- 通知受影响的业务或用户。
- 修正后以新版本重新发布。

删除向量不是完整的知识失效机制，缓存、重排索引、答案存档和引用记录也需要处理。

## 十九、冲突知识的处理

检索到相互冲突的制度时，不应让模型自行选择“看起来合理”的一个。

可以依据：

- 权威级别。
- 适用机构与业务范围。
- 生效和失效时间。
- 新旧替代关系。
- 制度所有者确认。

无法通过确定性规则解决时，应：

```text
明确展示冲突来源
→ 不生成确定性结论
→ 转制度所有者或合规人员确认
```

## 二十、没有可靠证据时怎样回答

RAG 系统需要允许“无法回答”：

```text
未在当前用户有权访问且处于生效状态的制度中找到充分依据。
建议补充问题范围或联系制度所有者确认。
```

不能因为检索为空就：

- 放宽权限搜索其他部门文档。
- 使用已失效版本替代。
- 让模型依赖通用知识猜测内部制度。
- 隐藏证据不足并给出肯定答案。

## 二十一、缓存设计

RAG 可能缓存：

- 查询改写结果。
- 检索结果。
- Embedding。
- 模型答案。

缓存键至少需要考虑：

```text
规范化问题
知识版本
用户或权限范围
业务目的
模型与 Prompt 版本
```

不能让用户 A 命中的高权限检索结果，被用户 B 从共享缓存中直接读取。

## 二十二、审计与隐私

建议记录：

- 谁以什么业务目的发起查询。
- 当时的权限上下文。
- 查询了哪些索引和知识版本。
- 返回了哪些文档与 Chunk 标识。
- 最终答案引用了哪些来源。
- 使用了哪个模型、Prompt 和检索配置。
- 是否发生拒绝、无结果、冲突或人工升级。

审计记录不代表要无条件保存完整问题、原文和模型上下文。应按照数据分级实施最小化、脱敏和保留期限。

## 二十三、RAG 评估指标

### 数据与索引质量

- 文档解析完整率。
- 元数据完整率。
- 生效版本同步延迟。
- 重复和孤立 Chunk 比例。

### 检索质量

- Recall@K：正确证据是否进入前 K 个候选。
- Precision@K：前 K 个候选中有多少真正相关。
- 重排后首条正确证据比例。
- 无结果与错误权限结果比例。

### 答案质量

- 答案正确性。
- 引用正确率和引用完整率。
- 答案是否被证据支持。
- 不充分证据下正确拒答率。

### 安全与治理

- 越权检索成功数，目标为零。
- 已失效知识被当前答案引用数，目标为零。
- 跨机构缓存泄漏数，目标为零。
- 知识撤回影响追踪完整率。

## 二十四、制度问答 RAG 全链路

```text
1. 用户在制度问答应用提问
2. API Gateway 验证用户和应用身份
3. Policy Service 计算知识访问范围和业务目的
4. Query Service 进行问题标准化与必要的查询改写
5. Retriever 在授权范围内执行关键词与向量检索
6. 返回结果再次进行权限、版本和生效状态检查
7. Reranker 结合相关性、权威性和时效排序
8. Context Builder 选择最少充分证据并加入来源信息
9. Model Gateway 调用批准的模型生成结构化答案
10. Citation Validator 校验引用存在、权限、版本和支持关系
11. Policy 执行输出安全检查
12. 应用展示答案、引用、适用范围和更新时间
13. Audit Service 记录证据链与版本
14. 用户可以反馈答案是否有帮助或申请人工确认
```

## 二十六、项目经理评审清单

### 知识接入

- 权威来源和文档所有者是谁？
- 草稿、重复和失效文档怎样识别？
- OCR、表格和附件质量怎样验证？
- 元数据是否支持权限、版本和引用？

### 检索与生成

- 权限过滤发生在检索前还是检索后？
- 是否结合关键词和语义检索？
- 重排是否考虑权威性和时效？
- 没有证据和证据冲突时怎样停止？

### 版本与运营

- 新制度多久能在问答中生效？
- 旧版本和缓存怎样失效？
- 能否追踪引用错误文档的历史答案？
- 是否有固定测试集验证升级后的检索质量？
