## 一、本课目标

完成本课后，你应该能够：

1. 解释 Human-in-the-loop（HITL）不只是“最后让人点一下确认”。
2. 判断人工应在行动前、执行中还是结果后介入。
3. 根据业务风险设计自动执行与人工审批矩阵。
4. 说明任务怎样安全地暂停、保存状态并恢复。
5. 设计审批、权限、审计、超时与紧急停止机制。
6. 为银行 KYC Agent 划定 Agent、平台和 Auditor 的职责边界。

## 二、什么是 Human-in-the-loop

Human-in-the-loop 是把有权限、承担相应职责的人嵌入 AI 系统的决策或执行过程。

```text
Agent 提出建议或行动
        ↓
平台依据策略判断风险
        ↓
低风险：自动继续
高风险或不确定：暂停并请求人工处理
        ↓
人工批准 / 修改 / 拒绝 / 要求补充 / 升级
        ↓
平台校验决定并恢复或终止任务
```

HITL 的目的不是证明模型一定正确，而是：

- 防止未经授权的高影响行动。
- 让业务责任人处理模糊、异常和冲突案例。
- 在执行前修正参数和范围。
- 为关键决定留下可追溯记录。
- 在自动化失效时提供安全接管路径。

人工批准本身也可能出错，因此它只是控制措施之一，不能替代数据校验、权限检查和系统测试。

## 三、人工介入的三个位置

### 1. 行动前：防止高风险操作发生

Agent 已经提出工具调用，但工具还没有真正执行。

```text
建议操作：向客户发送“补充受益所有人材料”通知
审批人看到收件人、模板、原因和证据
审批后才允许发送
```

适合：外部通信、写入业务系统、改变客户状态、产生资金或合规影响的操作。

### 2. 执行中：处理异常和新信息

Agent 执行到一半，环境反馈使原计划不再安全。

```text
KYC 系统姓名与申请材料不一致
        ↓
暂停自动流程
        ↓
Auditor 决定要求补件、继续核验或升级调查
```

适合：证据冲突、权限变化、工具连续失败、异常分数或计划需要重大修改。

### 3. 结果后：审核建议而非授权动作

Agent 已完成报告或建议，但结果尚未成为正式业务决定。

```text
Agent 生成 KYC 画像和审查建议
        ↓
Auditor 检查证据和可信度
        ↓
Auditor 作出最终审查决定
```

适合：报告签发、KYC 结论、信贷或合规建议等需要责任人判断的输出。

## 四、人工可以做哪些决定

审批界面不应只有模糊的“确认”按钮，至少要定义以下语义：

| 决定 | 含义 | 后续动作 |
| --- | --- | --- |
| Approve | 同意执行当前精确行动 | 执行已批准的参数 |
| Edit | 修改部分参数后批准 | 重新校验修改后的行动 |
| Reject | 不允许执行 | 终止该行动并记录理由 |
| Request information | 当前证据不足 | 补充信息后重新评估 |
| Escalate | 超出当前审批人权限 | 转交更高权限或专业人员 |

“修改后批准”必须重新进行权限和参数校验，不能因为修改者是人工就绕过平台策略。

## 五、按风险决定是否需要人工

不应让人工审批 Agent 的每一步，否则系统会变成昂贵而缓慢的手工作业。可以从影响、可逆性、权限和不确定性四个维度判断。

| 行动等级 | 银行场景示例 | 建议控制 |
| --- | --- | --- |
| 低风险只读 | 读取当前 Case 已授权的材料状态 | 权限校验后自动执行并记录 |
| 低风险生成 | 生成内部摘要草稿、整理证据目录 | 自动生成，发布前校验 |
| 中风险可逆写入 | 给 Case 添加内部标签或待办 | 规则允许时自动；异常时审批 |
| 高风险外部行动 | 向客户发送通知、提交正式报告 | 行动前人工批准 |
| 高风险业务决定 | 通过或拒绝 KYC、限制账户 | 授权人员作最终决定 |
| 不可逆或重大影响 | 资金转移、生产配置变更 | 强认证、多重控制，通常不交由 Agent 自主执行 |

触发 HITL 的条件可以包括：

- 行动影响客户权益、资金、账户或正式记录。
- 行动不可逆或回滚成本高。
- 模型置信度低，但不能只依赖模型自报分数。
- 关键数据缺失或多个系统的信息冲突。
- 工具或数据范围超出当前 Case 授权。
- 命中敏感客户、异常交易或特殊业务规则。
- Agent 计划发生重大变更，或接近步数、时间、成本上限。

## 六、职责分离：谁提议，谁授权，谁执行

一个稳健的结构是：

```text
LLM / Agent：提出行动和理由
Policy Engine：确定行动是否允许、是否需要审批
Authenticated Human：在本人权限范围内作出决定
Tool Runtime：只执行通过校验的精确行动
Audit Service：记录全流程
```

其中：

- LLM 不应自行决定“这个动作无需审批”。
- 提出行动的人或模型不等于授权人。
- 审批人不能批准超出其角色和数据范围的操作。
- Tool Runtime 不能接受任意自然语言并直接执行高风险指令。
- 高风险流程可以采用双人复核或职责分离，但具体规则应由本机构制度确定。

## 七、一个有效审批请求应该展示什么

审批人需要知道自己究竟在批准什么：

```text
Case：KYC-2026-00128
建议行动：向客户请求补充材料
工具：customer_notification.send
对象：指定客户及已验证联系方式
参数：材料类型、截止日期、消息模板版本
触发原因：受益所有人证明已过期
证据：KYC 系统记录与材料编号
潜在影响：客户收到外部通知
可逆性：消息发送后不可撤回
Agent 建议：发送；可信度仅作参考
```

审批界面应避免：

- 只显示“Agent 请求调用工具，是否批准”。
- 隐藏收件人、金额、时间范围等关键参数。
- 用很长的模型解释掩盖真正的操作内容。
- 将敏感原始数据展示给没有权限的审批人。

## 八、批准必须绑定到精确行动

批准不能是一张可以被重复或扩大使用的“空白支票”。它应绑定到：

- Case ID、任务 ID 和行动 ID。
- 工具名称与版本。
- 精确参数及其不可变摘要或哈希。
- 数据范围和目标资源。
- 审批人身份、角色和审批时间。
- 有效期和允许执行次数。

如果收件人、金额、材料类型、工具参数或计划版本发生变化，原批准应失效并重新审批。

## 九、暂停与恢复：HITL 是状态管理问题

任务等待人工时不能一直占用一个运行进程。平台通常需要保存检查点：

```text
RUNNING
   ↓ 遇到审批点
WAITING_FOR_HUMAN
   ↓ 保存检查点并释放运行资源
APPROVED / EDITED / REJECTED / EXPIRED
   ↓
RESUMED / CANCELLED / ESCALATED
   ↓
COMPLETED / FAILED
```

检查点至少应保存：

- 任务、Case 和会话标识。
- 已完成步骤及其经过验证的结果。
- 当前待审批行动和参数版本。
- 请求审批的原因和所需角色。
- 审批状态、截止时间和升级路径。
- 恢复执行所需的最小上下文。

恢复时必须再次验证：

1. 审批人身份与当前权限是否有效。
2. 审批是否仍在有效期内。
3. 待执行行动是否与被批准版本完全一致。
4. Case、数据或外部环境是否发生关键变化。
5. 该行动是否已经执行过。

## 十、幂等性：避免恢复后重复执行

部分 Agent 框架恢复时会从被中断节点的开头重新运行。如果暂停前已经执行外部副作用，就可能重复发消息、重复建工单甚至重复交易。

因此应：

- 把审批点放在外部副作用之前。
- 为每个行动生成唯一的 `action_id` 或幂等键。
- 工具执行前检查该行动是否已经成功完成。
- 将执行结果原子化记录，避免“执行成功但状态未保存”。
- 对不可幂等操作设计明确的补偿或人工接管方案。

## 十一、KYC Agent 的完整执行示例

```text
1. 接收 KYC Case 和 Auditor 身份
2. 平台验证 Case 范围与只读数据权限
3. Agent 读取授权的客户、材料和 AML 摘要
4. 规则检查材料缺失、过期和字段冲突
5. LLM 整理 KYC 画像、证据和待确认问题
6. Reflection 检查引用、完整性和越权措辞
7. 若需要补件，生成通知草稿并暂停
8. Auditor 批准、修改、拒绝或升级
9. 平台重新校验权限和精确参数
10. 受控工具发送通知或更新 Case 待办
11. Agent 等待材料，不擅自得出负面结论
12. 材料齐备后生成审查建议
13. Auditor 作出最终结果确认
14. 平台归档证据、决定和执行记录
```

职责边界：Agent 可以收集、比对、总结和提出建议；Auditor 对正式 KYC 结果负责。发现资料缺失时，应请求补充或转人工，不应直接推断客户存在风险。

## 十二、失败、超时和升级

HITL 流程不能无限等待。项目设计需要回答：

- 审批请求的 SLA 是多少？
- 超时后是提醒、重新分配、升级还是取消？
- 审批人请假或离职时如何转交？
- Case 或权限变化后怎样撤销待审批任务？
- Agent 或工具版本更新后，旧审批是否仍有效？

推荐明确状态，而不是把所有情况都记成“失败”：

```text
WAITING_FOR_HUMAN
APPROVAL_EXPIRED
REJECTED_BY_HUMAN
ESCALATED
PERMISSION_REVOKED
ACTION_ALREADY_EXECUTED
RESUME_FAILED
```

达到重试、步数、时间或成本上限时，应安全停止并转人工，而不是为了“完成目标”绕过控制。

## 十三、审计日志记录什么

建议记录：

- 谁、何时、以什么角色发起和审批。
- Agent、提示模板、策略和工具的版本。
- 原始行动建议和最终被批准的精确参数。
- 审批人选择的决定与结构化理由。
- 采用了哪些证据及其来源标识。
- 权限校验、策略命中和执行结果。
- 任务暂停、恢复、超时、撤销和升级事件。
- 人工对 Agent 建议做了哪些修改。

审计不等于无限保存所有内容。应依据数据分级和保留策略处理敏感信息，并避免为了审计而保存模型的隐藏思维过程。更有价值的是保存输入依据、可见建议、工具调用、决策和结果。

## 十四、紧急控制

即使已有审批，平台仍需准备应急手段：

- 暂停某个任务或某类 Agent。
- 禁用一个工具、数据源或模型版本。
- 撤销尚未执行的批准。
- 降级为只读或纯建议模式。
- 对异常调用量、重复行动和越权尝试告警。
- 将未完成 Case 批量移交人工队列。

紧急停止之后，系统还应保留现场状态，支持分析哪些行动已执行、哪些尚未执行，以及是否需要补偿处理。

## 十五、为什么要防止 Excessive Agency

Agent 拥有的工具、权限和自主范围超过完成任务所需，就形成“过度代理能力”风险。模型幻觉、错误上下文或提示注入可能借此转化为真实业务影响。

控制原则包括：

- 最小权限：只开放完成当前任务所需的工具和数据。
- 最小自主性：能以只读或生成草稿完成，就不授予写入权限。
- 确定性策略：高风险行动由平台规则拦截，不由模型自判。
- 人工批准：对重大影响行动增加授权人确认。
- 参数约束：工具接口使用结构化字段、范围限制和白名单。
- 防御纵深：HITL、权限、验证、监控和审计共同工作。

特别注意：来自客户材料、网页、邮件或知识库的文本都可能包含恶意指令。它们应被视为业务数据，而不是可以覆盖系统策略的命令。

## 十六、治理指标

项目经理可以跟踪：

| 指标 | 观察的问题 |
| --- | --- |
| 自动处理率 | 哪些低风险步骤已稳定自动化 |
| 人工介入率 | HITL 是否过多或过少 |
| 批准、修改、拒绝率 | Agent 建议质量和策略匹配度 |
| 人工处理时长 | 审批是否成为瓶颈 |
| 超时与升级率 | 队列和职责设计是否合理 |
| 越权尝试拦截数 | 权限边界是否有效 |
| 恢复失败率 | 检查点和运行状态是否可靠 |
| 重复副作用次数 | 幂等控制是否有效 |
| 人工推翻率 | 最终结果是否经常偏离 Agent 建议 |
| 审计完整率 | 关键决定能否追溯到证据和责任人 |

不能仅追求较高自动处理率。对高风险流程来说，准确转人工和安全停止本身就是成功结果。

## 十七、概念代码

下面是框架无关的 Python 伪代码，重点在职责和状态，而不是具体语法：

```python
def execute_agent_action(task, proposed_action, policy, checkpoint_store):
    decision = policy.evaluate(task, proposed_action)

    if not decision.allowed:
        return stop_task("POLICY_DENIED")

    if decision.requires_human:
        checkpoint_store.save(
            task_id=task.id,
            status="WAITING_FOR_HUMAN",
            action=proposed_action,
            action_hash=hash_action(proposed_action),
            required_role=decision.required_role,
            expires_at=decision.expires_at,
        )
        return request_human_decision(task.id)

    return run_idempotently(proposed_action)


def resume_after_review(task, review, policy, checkpoint_store):
    pending = checkpoint_store.load(task.id)

    policy.validate_reviewer(review.user, pending.required_role)
    policy.validate_not_expired(pending.expires_at)
    policy.validate_action_hash(pending.action, pending.action_hash)

    if review.type == "REJECT":
        return stop_task("REJECTED_BY_HUMAN")

    if review.type == "EDIT":
        return execute_agent_action(task, review.edited_action, policy,
                                    checkpoint_store)

    return run_idempotently(pending.action)
```

这里体现了五个关键点：策略先行、持久化暂停、审批人鉴权、批准绑定行动、幂等执行。

## 十八、项目经理设计清单

### 业务与风险

- 哪些结果只是参考，哪些会成为正式决定？
- 哪些行动影响客户、资金、合规或生产系统？
- 哪些异常必须立即转人工？
- 人工审批是否真的能降低该风险？

### 权限与审批

- 谁可以批准哪类行动和数据范围？
- 是否需要双人复核或职责分离？
- 人工可以批准、修改、拒绝、补件还是升级？
- 参数变化后是否强制重新审批？

### 运行与恢复

- 检查点保存在哪里，保留多久？
- 审批超时如何处理？
- 恢复时怎样防止重复执行？
- 如何取消任务、撤销批准和紧急停用工具？

### 审计与运营

- 是否能追溯到证据、策略、工具版本和审批人？
- 日志是否遵守敏感数据和保留要求？
- 哪些指标用于发现流程瓶颈和风险？
- 如何采集人工修改，用于改进而不直接污染生产策略？

## 二十、本课学习方式

### 第一段：理解介入点与审批矩阵，约 30 分钟

阅读第二至第五节，重点理解“何时需要人”而不是“所有步骤都让人确认”。

### 第二段：理解执行治理，约 40 分钟

阅读第六至第十四节，掌握职责分离、行动绑定、暂停恢复、幂等、审计和紧急控制。

### 第三段：应用到 KYC Agent，约 25 分钟

阅读第十一、十五至十八节，把控制机制映射到自己的 KYC 场景。

## 二十一、轻量练习

完成对应学习段后再作答，不需要一次做完：

1. 将 KYC Agent 的五个行动分为自动执行、单人审批、升级审批三类，并说明理由。
2. 设计一张“请求客户补充材料”的审批卡片，列出审批人必须看到的信息。
3. 描述一次任务从暂停、人工修改到恢复执行的过程，并指出怎样防止重复发送通知。

## 二十二、本课验收标准

- [x] 能解释 HITL 的目的以及它为什么不等于结果正确。
- [x] 能区分行动前、执行中和结果后三种人工介入位置。
- [x] 能按影响、可逆性、权限和不确定性设计审批矩阵。
- [x] 能解释提议者、策略、授权人和执行器的职责分离。
- [x] 能说明批准为什么必须绑定到精确行动。
- [x] 能描述任务暂停、检查点保存和恢复校验过程。
- [x] 能解释幂等性怎样避免重复副作用。
- [x] 能为 KYC Agent 设计审计、超时、升级和紧急停止机制。
